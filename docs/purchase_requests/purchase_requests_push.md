## Важное замечание

- **Кому уходит push:** ровно тем, кому база записала уведомление, — участникам роли **текущего этапа** (как и раньше) плюс **инициатору** по согласованиям, оплате и получению.
- **Секреты не добавляются.** Edge Function использует те же `SERVICE_ACCOUNT` и `SUPABASE_SERVICE_ROLE_KEY`, что и push по сменам.
- **Конфигурация Firebase публичная** и лежит в коде: `react_app/src/config/firebase.ts` и `react_app/public/sw.js` (дублируется, менять в обоих файлах).
- **Service worker один.** Push добавлен в существующий `react_app/public/sw.js`. Отдельный `firebase-messaging-sw.js` создавать нельзя — он вытеснит текущий воркер с той же областью видимости.
- **Telegram не используется** — по решению заказчика.

## Описание

Push приходит на телефон и на компьютер при действиях по заявке.

| Событие | Кому уходит push |
|---------|------------------|
| Отправка на согласование (и повторная) | все «Первый согласующий» |
| Заявка согласована | все «Подготовка счетов» **+ инициатор** |
| Возврат заявки на доработку | инициатор |
| Счета отправлены на согласование | все «Согласование счетов» |
| Счета согласованы | все «Бухгалтер» **+ инициатор** |
| Счета возвращены на доработку | все «Подготовка счетов» **+ инициатор** |
| Заведено на оплату | **инициатор** |
| Оплачено | получатели (при «назначенные сотрудники») **+ инициатор** |
| Получено | **инициатор** |

Инициатор не получает уведомление о собственном действии.

## Архитектура

```
Клиент (сайт react_app или мобильное приложение)
   │  1. RPC: смена статуса заявки
   │     (внутри базы пишутся строки purchase_request_notifications)
   │  2. functions.invoke('send_purchase_request_event', { request_id })
   ▼
Edge Function send_purchase_request_event
   │  3. Читает уведомления заявки с pushed_at IS NULL — это и есть получатели
   │  4. Берёт активные токены устройств из user_tokens
   │  5. Отправляет FCM (web → webpush; ios/android → notification + apns)
   │  6. Помечает уведомления pushed_at = now()
   ▼
Firebase Cloud Messaging → браузер / iPhone / Android
```

Получатели **не дублируются** в Edge Function: единственный источник правды — таблица уведомлений, которую пишет база. Если правила этапов изменятся, push поедет за ними автоматически.

## База данных

### Таблица `public.purchase_request_notifications`

Добавлена колонка:

| Колонка | Тип | Описание |
|---------|-----|----------|
| `pushed_at` | timestamptz | Когда push отправлен. Заполняет Edge Function |

Индекс: `idx_purchase_request_notifications_pending_push (request_id) WHERE pushed_at IS NULL`.

### Триггер `purchase_request_history_notify_creator`

`AFTER INSERT ON public.purchase_request_history` → `purchase_request_internal_notify_creator_on_action()`.

Пишет уведомление инициатору по кодам действий: `approved`, `invoice_approved`, `invoice_returned`, `queued_for_payment`, `paid`, `received`.
`returned` (возврат заявки) не обрабатывается — инициатора уведомляет сам RPC `purchase_request_return`.

Функция `SECURITY DEFINER`: RLS на таблице уведомлений не мешает записи.

**Миграция:** `supabase/migrations/20260915120000_purchase_request_push_notifications.sql`.

## Edge Function `send_purchase_request_event`

**Путь:** `supabase/functions/send_purchase_request_event/index.ts`
**Auth:** `verify_jwt = true`

### Вход

| Поле | Тип | Описание |
|------|-----|----------|
| `request_id` | UUID | заявка |
| `origin` | string? | адрес сайта для перехода по push (только для web) |

### Поведение

1. Проверяет, что вызывающий — активный участник компании заявки (иначе 403).
2. Читает `purchase_request_notifications` заявки с `pushed_at IS NULL`.
3. Отключает получателей с `profiles.status = false`.
4. Берёт активные токены (`platform` ∈ `ios`/`android`/`web`), один токен на устройство (`installation_id`).
5. Отправляет FCM. Для web — только `webpush` (иначе два баннера), ссылка `{origin}/purchase-requests?requestId=<id>`.
6. Помечает уведомления отправленными, даже если токенов не нашлось — повторной отправки не будет.

### Секреты

| Секрет | Назначение |
|--------|------------|
| `SERVICE_ACCOUNT` | JSON сервисного аккаунта Firebase (уже настроен) |
| `SUPABASE_SERVICE_ROLE_KEY` | чтение токенов и уведомлений (есть по умолчанию) |

Новых секретов не требуется.

### Особенность self-hosted: проверка JWT

На сервере переменная окружения `VERIFY_JWT=false`, поэтому платформенной проверки токена нет — **её делает сама функция**: вызывает `auth.getUser()` и проверяет, что вызывающий состоит в компании заявки. Без входа ответ `401 {"error":"unauthorized"}`.

Миграция применена со стороны платформы, поэтому её версия в истории БД отличается от имени файла в репозитории (как у остальных миграций проекта).

## Ограничения

- **iOS: push только у приложения, установленного на экран «Домой».** Во вкладке Safari Web Push не работает — системное ограничение Apple.
- **Если действие выполнили из клиента без обновления** (старая сборка мобильного приложения или сайта), push не уйдёт: вызов делает клиент. Уведомление при этом в базе останется и уйдёт при следующем действии.
- **Переход по push у неавторизованного** ведёт на вход; адрес заявки после входа не сохраняется.
- **Ленты уведомлений внутри приложений нет** — только push.
